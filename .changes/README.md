# Change files

`CHANGELOG.md` is generated by [changie](https://changie.dev) from the files in this directory. Edit these, not the
changelog.

- `unreleased/` holds one YAML file per change that has not shipped yet.
- `v*.md` holds the notes for each release. `v1.11.1.md` carries every release up to and including 1.11.1.
- `header.tpl.md` is the top of `CHANGELOG.md`.

changie runs as a Go tool from `tools/go.mod`, so nebula's own `go.mod` does not depend on it:

```sh
go tool -modfile=tools/go.mod changie <command>
```

## Adding an entry

Run `make changelog`, pick a kind, and write the entry the way it should read in the release notes. Commit the file
it creates under `unreleased/` with the rest of the PR. A bot comment on the PR shows its change files, or explains
how to add one. The Changelog check fails a PR that adds no change file, unless it's labeled `skip-changelog`
(nothing users would notice) or `dependencies`.

Kinds follow [Keep a Changelog](https://keepachangelog.com/en/1.0.0/): Added, Changed, Deprecated, Removed, Fixed,
and Security.

## Releasing

Every push to `master` or a `release-*` branch with files in `unreleased/` opens or updates a "vX.Y.Z changelog" PR
from `changie-release/<branch>`. It batches the files into `.changes/vX.Y.Z.md` and regenerates `CHANGELOG.md`. On
`master` the version comes from the kinds (Added, Changed, Deprecated or Removed bump the minor version; Fixed and
Security bump the patch); on a release branch it is always a patch release.

Merging that PR tags the merge commit, and the tag runs the release workflow, which publishes `.changes/vX.Y.Z.md`
as the GitHub release notes. Every run tags the newest version in `.changes/` if its tag doesn't exist yet, so
rerunning the workflow retries a release that didn't get tagged.

Without a `RELEASE_TOKEN` secret, the workflow pushes with `GITHUB_TOKEN`. A maintainer then approves the checks on
the release PR, and the workflow dispatches the release workflow on the tag itself. To add the milestone link or reword an entry, edit `.changes/vX.Y.Z.md` on the release
PR's branch and run `make changelog-merge`. The next push to the base branch rebuilds the release PR and drops
those edits, so make them right before merging.

## Backports

A cherry-picked change file keeps its name. When a patch release from a `release-*` branch is tagged, a
`changie-sync/vX.Y.Z` PR copies its notes to `master` and deletes the change files it batched, so the next minor
release doesn't list them again.
